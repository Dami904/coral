OVERVIEW / INTRODUCTION

Introduction

An on-chain agent that checks its own memory before it ever spends - a smart contract, not its own judgment, decides whether it's allowed to.
Base mainnet - live Base Sepolia - live 155 unit tests 56 Foundry tests

The problem

"Is this token worth looking at?" gets asked hundreds of times about the same handful of contracts. Sibyl Labs' x402 Intelligence Endpoint answers that with a real builder-conviction score - for a real price, $0.25 per fresh evaluation, confirmed live, not assumed. Paying for a fresh check on every single ask is wasteful. Never checking is unsafe. Forgetting a verdict already paid for is worse than either.

Coral caches what it learns in Sibyl Memory, so it only pays once per contract per staleness window. The whole project is judged on one gate: delete Sibyl Memory's SQLite file, and the next lookup for a contract Coral answered a minute earlier is a genuine cache miss again - it pays again, on real money, because the thing it would have remembered is gone.

Unlike the hired-agent side, this isn't "generalized, one implementation so far." Sibyl Memory is the hackathon's own mandatory, judged requirement, and the only memory backend Coral has ever used, full stop. MemoryPort exists purely as a unit-test seam, to inject fakes in test/decisionCore.test.ts and friends, not as an invitation to swap in a different memory provider - there is no other one.

Built for

Sibyl Labs Hackathon (Sep 1–10, 2026). Source: github.com/Dami904/coral. Landing page: dami904.github.io/coral.

OVERVIEW / HOW IT WORKS

How it works

One function runs the entire critical path, and memory is checked before the chain is ever touched.

The decision flow

handleJobQuery in src/decisionCore.ts - not an optimization, an invariant.

  1. Receive - a query for a contract address arrives (free HTTP, Ping, or an ACP job).
  2. Recall - Sibyl Memory is checked first. A fresh hit answers instantly, free, no chain call at all.
  3. Decide - a real miss hands the decision to SpendGuard, a deployed contract, not the agent's own reasoning.
  4. Pay, cache, journal - only once payment clears does Coral call Sibyl and cache the result. The payment is journaled to memory before that call, so even a downstream failure leaves a reconcilable trail.

One hired agent today, by design not by limitation

handleJobQuery never hardcodes Sibyl. It takes a hiredAgentId (an opaque string) and an IntelligencePort - a generic invoke(input, txHash) -> output interface any hired agent could sit behind, and the cache key partitions by that id so two different agents' answers never collide.

That said, be precise about what exists right now: X402IntelligenceClient, wired to Sibyl's real x402 endpoint, is the only real implementation of that interface in this codebase today. Nothing else is plugged in, and nothing else has been paid. Adding a second hired agent means writing and independently verifying a new adapter for that agent's real request/response contract first - the architecture is ready for it, but "ready" isn't "done."

SpendGuard's four rules

Coral's wallet can only ever request a payment - it never holds direct transfer authority. Every request is checked against four rules, in this fixed order, every time.

#RuleWhat it enforces
01AllowlistOnly pre-approved recipient addresses can ever receive funds.
02Max per paymentA hard ceiling no single request can exceed, approved or not.
03Budget windowA rolling spend cap over a fixed time window, not per-call alone.
04Rate limitA cap on how many payments can fire within that same window.

Above a configurable humanApprovalThreshold, even a request that clears all four rules doesn't execute - it waits for a separate, human-signed ownerApprove call. Policy changes and withdrawals go through a mandatory 1-hour queue-then-execute timelock, so even a compromised owner key can't rewrite the rules instantly.

ON-CHAIN PROOF / A BUG, FOUND LIVE

A real bug, found live

Sibyl's own documentation doesn't match Sibyl's own API.

What happened

Sibyl's endpoint self-documents its paid response as {"tier": "high_conviction", ...}. The first real mainnet ACP job delivered {"output":"unknown",...} instead - a completed job, real payment, real HTTP 200, no error anywhere, and silently wrong data.

// real response, WETH, Base mainnet
{
  "agent": "SIBYL #20880",
  "conviction_score": 19,
  "conviction_tier": "medium",   // the real field - docs say "tier"
  "summary": "WETH conviction score: 19/30 (medium)..."
}

Root cause

X402IntelligenceClient.deriveTier() only checked for a tier key, which the real response doesn't have.

Fix

Checks the confirmed-live conviction_tier field first, falls back to tier only if absent (in case a different Sibyl API version genuinely uses it). Mock server's wire shape updated to match. All 155 tests pass after the fix, redeployed to the live ACP provider the same session it was found.

Trust model

Exactly what's live, what's staged, and the known limitations.

What's live vs. staged

PieceStatusDetail
Sibyl MemoryLiveReal sibyl-memory-mcp over stdio, real SQLite, deletion-tested against both deployed contracts.
SpendGuard, testnetLiveDeployed to Base Sepolia; timelocked policy, fixed-capacity ring buffers, two-step ownership.
SpendGuard, mainnetLiveDeployed, verified, funded, and paid out real USDC via a real policy today.

Free HTTP gatewayTestnet onlyWired to the mock evaluator on purpose - flipping to real mainnet money needs the same fix already applied to ACP.
Ping messagingStagedBuilt and unit-tested against the real SDK. No testnet exists for Ping - a real send is real, public, irreversible mainnet spend, held for a deliberate go-ahead.
Gateway mode (paid, via Ping)StagedAnother agent pays Coral over Ping for the same lookup. Unit-tested against decoded receipts, not yet exercised against a real paying counterparty.

Known limitations

  • Not a safety verdict. Sibyl's score is builder conviction / community seed / on-chain proof of work - never a scam or rug-pull check.
  • Budget/rate logs are fixed-capacity by design. Policy can be tightened freely post-deploy; loosening past the provisioned capacity needs a new deployment.
  • Single-EOA owner, no multisig yet. Bounded by the 1-hour timelock; two-step ownership transfer means a Gnosis Safe can be swapped in later with zero contract changes.
  • In-memory pending-request tracking. A process restart loses track of any escalation mid-flight.
  • The 120-second x402 relay window is real and can be lost - observed live on this project's own first mainnet payment. Raising the auto-pay threshold above the real price removes the race for ordinary queries.
